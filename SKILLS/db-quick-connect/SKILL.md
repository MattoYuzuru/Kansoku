# db-quick-connect

Fast path to the local Postgres instance for debugging — schemas, tables, ad-hoc queries —
without re-deriving connection details or touching real secrets each session.

## Where the credentials/config actually live (don't invent new ones)

Nothing here is hardcoded. These are pointers to files/env vars that already exist once the
stack has been brought up per `README.md` → "Быстрый старт":

| What | Where | Notes |
|---|---|---|
| DB password | `deploy/secrets/database_password` | Local file, `chmod 600`, gitignored. Generated by the Quick Start step (`openssl rand -base64 32`). Only the `kansoku` binary itself needs to read this — see below, you usually don't. |
| Non-secret DB config | `deploy/runtime-config.json` → `.database` | host `postgres`, port `5432`, db `kansoku`, user `kansoku`, `sslmode=disable`. Validated verbatim by `internal/runtime/config.go` (`c.Database.*` checks) — don't expect anything else to work in the compose stack. |
| Secret file mapping | `deploy/runtime-config.json` → `.secret_files` | Maps each secret name to its `/run/secrets/*` path inside the container. |
| Integration-test DSN | env var `KANSOKU_TEST_POSTGRES_DSN` | Set by `scripts/validate_runtime.py` / `validate_data_platform.py` / `validate_integrity.py` when they spin up a pinned, ephemeral Postgres 18 for the `postgres_integration` build-tag tests. If it's set, a real host-reachable DSN already exists — use it directly. |

**Important:** in `deploy/compose.yaml`, the `postgres` service has no `ports:` mapping and sits
only on `kansoku-internal`, which is `"internal": true`. It is **not reachable from the host**
by design (see the ADRs under `adr/` for the hardening rationale) — you cannot `psql -h
127.0.0.1` into it. The only way in from a dev shell is through the container itself.

## Quickest path: psql via the running compose stack

```bash
cd deploy

# Interactive shell (local unix-socket connection inside the container uses trust auth —
# no password prompt, so you never need database_password for this).
docker compose -f compose.yaml exec postgres psql -U kansoku -d kansoku

# One-off query
docker compose -f compose.yaml exec -T postgres psql -U kansoku -d kansoku -c \
  "SELECT schema_name FROM information_schema.schemata ORDER BY 1;"
```

Useful psql commands once inside:
- `\dn` — list schemas
- `\dt <schema>.*` — list tables in a schema (`\dt public.*` for the app's own tables)
- `\d <table>` — describe a table

**Schema note:** production code (see `internal/dataplatform/migrate.go`,
`internal/runtime/migrate.go`, `internal/integrity/`) creates all real tables in the default
`public` schema — there's no separate prod schema per module. Non-`public` schemas only show up
transiently inside `*_integration_test.go` runs, which create randomly-named schemas
(`pgIdent(name)`) purely to isolate concurrent test runs; don't expect one in a normal running
dev stack.

## Python connector (`pg.py`)

Same rules, wrapped in a small script so you don't have to remember the `docker compose`
invocation or re-derive the DSN-vs-compose branch:

```bash
python3 SKILLS/db-quick-connect/pg.py schemas
python3 SKILLS/db-quick-connect/pg.py tables            # defaults to schema "public"
python3 SKILLS/db-quick-connect/pg.py tables <schema>
python3 SKILLS/db-quick-connect/pg.py query "SELECT * FROM schema_migrations;"
```

It never embeds a credential: if `KANSOKU_TEST_POSTGRES_DSN` is set it uses that (host-reachable
ephemeral test Postgres); otherwise it shells out to `docker compose exec` against the
`deploy/compose.yaml` stack exactly like the one-liners above. Requires `psql` on `PATH` for the
`KANSOKU_TEST_POSTGRES_DSN` branch, and a running `docker compose up` stack for the default
branch — it does not start or configure anything itself.

## Do NOT

- Do not read `deploy/secrets/database_password` (or any other file under `deploy/secrets/`) and
  print/log/paste its contents. You don't need it for the flows above; the container path uses
  trust auth, and if you ever do need the real DSN, build it in-process and pass it straight to
  the client without echoing it.
- Do not add a `ports:` mapping to `deploy/compose.yaml` to "make Postgres reachable" — that
  reverses a deliberate hardening decision (see `adr/`). Use `docker compose exec` instead.
- Do not commit anything from `deploy/secrets/` or `deploy/.env` — both are gitignored on
  purpose.
